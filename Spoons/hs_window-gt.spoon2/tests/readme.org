#+title: hs_window-gt's tests

These are the tests of hs_window-gt. They run inside the running Hammerspoon 2, because most of
the Spoon acts on real windows and screens. They are marked =export-ignore=, so users who install
the Spoon do not download them.

The harness, the runner, the test windows, the makefile and the self-tests are copies of the
files in =tests-common/= at the top of the repository, which every Spoon's tests share. They are
never edited here: a change is made in =tests-common/= and copied with =tests-common/sync=.
=tests-common/readme.org= explains this. The files particular to hs_window-gt are its
=*.test.js= files, =spoon.js= and this readme.

* Running the tests

The tests are run from the Spoon's directory, with Hammerspoon 2 running and =hs.ipc= started:

#+begin_src sh
make test                                     # every tests/*.test.js
make test TESTS="tests/selftest/*.test.js"    # the given files
#+end_src

=make= starts the tests at once, shows no chooser, and prints the results when the run
finishes. =tests/run= run directly, without =--no-confirm=, first shows a chooser in Hammerspoon 2
asking whether to start; that chooser closes, and the run is cancelled, when another window takes
the focus. The tests move windows and the pointer, so the mouse and the keyboard are left alone
from the start until the results are printed, or, with =tests/run=, until a chooser says that the
tests have finished, with their totals. That chooser asks whether the run was
uninterrupted. The results are printed once it is closed. When the answer is that the mouse or
the keyboard was used, =tests/run= says that the results may be wrong, and exits with 1.

Before the first test, the harness records the window in front on each screen, and the focused
window. After the last test, it focuses each of them again, the focused window last. The order of
the windows behind them is not restored, because macOS cannot send a window back.

The window recorded for a screen can be the wrong one. The harness takes the first window on each
screen in =hs.window.orderedWindows()=. That function does not return the windows in the order
they are stacked on screen, although its documentation says so. It returns every window of the
focused application first, then the windows of each other application. When the focused
application has a window on a screen that is covered by another application's window, the
covered window is recorded and brought forward. On 2026-11-23, with Google Chrome focused, a
Chrome window was brought forward on one screen instead of the kitty window that had been in
front of it. The user decided to leave this as it is.

** Which tests to run

A full run takes about ten minutes, and the mouse and the keyboard cannot be used meanwhile. Run
only the files that a change can affect, with =make test TESTS=...=. Run every file only when a
change can affect all of them, such as a change to =harness.js=, =fixture.js= or the Spoon's
=frameSet()=, or before a change to the Spoon is committed. =tests/run= then prints one line per test and exits with 0 when every test passed
or was skipped, 1 when a test failed or the run was cancelled, and 2 when the tests could not be
run or did not finish within =HS_WINDOW_TESTS_TIMEOUT= seconds (600 by default).

The tests in =tests/selftest/= check the harness itself. Two of them fail on purpose.

* How a run works

A run has four steps:

1. =tests/run= sends one line through =hs2=, which loads =tests/harness.js= and calls its
   =run()=. =hs2= does not wait for a promise, so =run()= returns at once and the tests continue
   inside Hammerspoon 2.
2. The harness loads a fresh copy of the Spoon from =../init.js=. =require()= caches a module
   under the path it was given, and the configuration loads the Spoon through its link in
   =Spoons/=, so this copy has its own state and its own =config=. =tests/spoon.js= then
   points its =attachFile= and =screenshotDir= into a temporary directory, so it never reads or
   writes the user's attached keys. The harness starts the copy before the tests and stops it
   afterwards.
3. Each test runs in turn. A test that takes longer than its timeout fails.
4. The harness writes a report, and =tests/run= prints it. The temporary directory is removed.

* Writing a test

A test file is named =<area>.test.js= and exports a list of tests. Each test has a =name=, a
=run= function, and optionally a =timeout= in seconds, which is 10 by default.

A test that fails because of a known defect outside this Spoon names it in =knownIssue=, such as
="Hammerspoon/Hammerspoon2#423"=. Its failure is reported as =KNOWN= and does not fail the run.
When such a test passes, it is reported as =FIXED=, which fails the run: the defect may have been
fixed, and =knownIssue= is removed from the test once that is confirmed. =run= may be
asynchronous, and receives one argument with these fields:

| Field         | Holds                                                                      |
|---------------+----------------------------------------------------------------------------|
| =spoon=       | The fresh copy of hs_window-gt                                             |
| =dir=         | The temporary directory of the run                                         |
| =spoonName=   | The Spoon's name, from its =spoon.json=                                    |
| =runId=       | A number unique to the run, which is part of every test window's title     |
| =titlePrefix= | The text every test window's title starts with, such as ="hs_window-gt test 1795391522729 "= |
| =assert=      | =ok(value, message)=, =equal(actual, expected, message)=, =fail(message)= and =frameEqual(actual, expected, message)= |
| =skip=        | =skip(reason)= ends the test and reports it as skipped                     |
| =wait=        | =wait(seconds)= returns a promise that resolves after that many seconds    |
| =windowsOpen= | =windowsOpen(count)= opens that many test windows, 1 by default, and resolves to their =HSWindow= objects |
| =windowOpenBorderless= | =windowOpenBorderless([title])= opens one borderless window, which is not standard and has no close button, with the title or with none, and resolves to it. It is closed through its process. |
| =windowTitleSet= | =windowTitleSet(window, title)= changes a test window's title, through a command file its process reads, and resolves when the window shows it |
| =cleanup=     | =cleanup(fn)= registers a function to run after the test, also when it fails; the last registered runs first |
| =windowClose= | =windowClose(window)= closes a test window with its close button, and resolves when it is gone |
| =frameSet=    | =frameSet(window, frame)= sets a window's frame and waits for it to take effect |
| =screenFrame= | =screenFrame(window)= returns the usable frame of the window's screen      |
| =screensNeed= | =screensNeed(count)= ends the test as skipped when fewer screens are connected |
| =alertsCapture= | =alertsCapture()= returns a list that receives the message of every alert shown until the test ends. The alerts are still shown. |
| =canvasesCapture= | =canvasesCapture()= returns a list that receives ={frame, canvas}= for every canvas created until the test ends. The canvases are still shown. |
| =promptCancel= | =promptCancel()= waits for a prompt of hs_interactive-gt to open and cancels it with Escape. It is called without =await=, before the function that prompts. |

#+begin_src js
module.exports = [
    {
        name: "leftHalf places the window on the left half of its screen",
        run: async (t) => {
            // ...
            await t.wait(0.3)
            t.assert.equal(window.frame.x, screen.x)
        }
    }
]
#+end_src

A test acts only on windows it opens with =windowsOpen()=. After each test the harness puts
the pointer back where it was, rounded to a whole point, and takes any test window out of
fullscreen before closing it. The Spoon's internal functions are
tested through the exported functions that use them.

* The test windows

=windowsOpen()= starts =tests/fixture-windows.jxa= with =osascript -l JavaScript=. That script
opens one plain Cocoa window for each title it is given and keeps them open until its process
ends. After each test, also when the test fails or times out, the harness closes every window
with its close button and then ends the process, so a test does not close its own windows. An
=osascript= icon is shown in the Dock while the process runs.

Three things about hs_windowfilter-gt decide how the windows are made and closed. hs_window-gt
learns that a window was focused, moved or closed only through hs_windowfilter-gt.

1. Its default filter, which hs_window-gt uses, leaves out Hammerspoon 2's own windows. The test
   windows therefore belong to a separate process rather than being made with =hs.ui.window()=.
2. It tracks only standard applications, those with an icon in the Dock. The process is
   therefore a regular application, and has an icon.
3. It reports =windowDestroyed= when a window is closed with its close button. Ending the
   process produced no event, and left the window in its list. A test that closes a window
   during the test does so with =windowClose()=, which uses the close button.

Three measurements, made on 2026-11-23, govern how frames are compared and chosen:

1. A window rounds each value of its frame to a whole point, and a value can move by up to one
   point in doing so: y = 200.25 was read back as 201. =assert.frameEqual()= therefore accepts
   a difference of 1 point in each value.
2. A test window cannot be smaller than 87 by 33 points, so a test does not ask for less.
3. The windows appear about 0.3 s after their process starts. =windowsOpen()= waits up to 5 s.

Expected frames are computed from =screenFrame()=, never from the size of one display.

* The tests that need two screens

Every test that needs two screens is in =tests/two-screens.test.js=, so that they can be run
together when a second screen is connected, for example an iPad through Sidecar:

#+begin_src sh
make test-two-screens
#+end_src

That file exports ={screens: 2, tests: [...]}= instead of a list. When fewer screens are
connected, the harness reports each of its tests as skipped without running them, and every
other file runs as usual. A test elsewhere that needs two screens for one check calls
=screensNeed(2)= instead, but such a test belongs in this file.
